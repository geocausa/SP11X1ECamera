## Distinguish the rails correctly

| Windows camera resource | Linux upstream reference | Provider |
|---|---|---|
| `PPP_RESOURCE_ID_LDO6_M` (sensor DOVDD and observed VCM I/O dependency) | `vreg_l6m_1p8: ldo6` | `qcom,pm8010-rpmh-regulators`, `qcom,pmic-id = "m"` |
| `PPP_RESOURCE_ID_LDO16_B` (VCM VDD per Haipeng) | `vreg_l16b_2p9: ldo16` | `qcom,pm8550-rpmh-regulators`, `qcom,pmic-id = "b"` |

The exact labels and PMIC IDs are found in **upstream**
`arch/arm64/boot/dts/qcom/x1e80100-qcp.dts` (reference board);
the PM8010 LDO6 and PM8550 LDO16 hardware resources are independently
present in `drivers/regulator/qcom-rpmh-regulator.c`. The Windows
CAMS_RES decoded resource names for this SP11 are recorded in
`experiments/E001-windows-oracle-map/derived/power-map.md`.

- **Never** confuse `vreg_l6b_1p8` (PMIC **B**, LDO6) with
  `vreg_l6m_1p8` (PMIC **M**, LDO6): they are different resources.
- The current upstream `x1-microsoft-denali.dtsi` has `regulators-0`
  (`pmic-id = "b"`) and the parent `vdd-l5-l16-supply = <&vreg_bob1>`
  but **no L16B ldo16 node**.
- It has no PM8010 `pmic-id = "m"` RPMh regulator provider for L6M.
  `hamoa-pmics.dtsi` does define an SPMI PM8010 peripheral; this does
  not by itself establish the board's input-supply wiring.
- `x1p64100-microsoft-denali.dts` and
  `x1e80100-microsoft-denali-oled.dts` both include
  `x1-microsoft-denali.dtsi`: an eventual common-scope change needs
  evidence for both LCD/X1P and OLED/X1E SKUs.

## Important unresolved electrical dependency

The upstream QCP board has
`vdd-l6-supply = <&vreg_s6g_1p8>` for PM8010 L6M. **Denali does not
define that QCP-only source regulator**. That parent phandle must not
be copied or replaced by an invented `vreg_s4c_1p8` mapping without
electrical evidence.

The PM8550 B block on Denali already declares
`vdd-l5-l16-supply = <&vreg_bob1>`, so its L16B parent is represented.
The exact L16B voltage selection requires confirmation: the Windows
resource requests 2,900,000 µV whereas QCP uses a 2,912,000 µV
constraint for its L16B. Do not infer that they program the same voltage
selector, or that a specific rounded voltage is SP11-validated.

For PM8010 L6M, first determine which input rail physically feeds
`vdd-l6` on Denali; verify the live RPMh command database resource
`ldom6` and the physical input mapping. Do not define a fixed-regulator
stand-in or `regulator-always-on` just to make focus work.

### Clarification on voltage and physical-versus-logical PMIC identity

The Windows resource value `0x2c4020` is **2,900,000** µV, not 2,904,000 µV.
The corresponding upstream QCP DTS constraint is 2,912,000 µV, so the
precise physical selector on Denali remains an unproven detail. The
PM8010 in `hamoa-pmics.dtsi` is an SPMI peripheral (address `0xc`);
the regulator's RPMh `qcom,pmic-id = "m"` is a separate logical
resource suffix. Do not equate them by their hexadecimal value.
