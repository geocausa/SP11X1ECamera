# E003h 0073 — exact sequential Tintless request5 → request6 replay

Status: **accepted Windows-live + offline ARM64 replay checkpoint, camera identity corrected to OV13858 rear mode 1**. No Linux camera runtime or Linux request6 is performed or authorized. See `LSC-TINTCTX-CAMERA-IDENTITY-CORRECTION.md`.

## Camera-identity correction

The original capture was initially described as front-camera state. Raw NTFS recovery later recovered request5 `x1`, whose Tintless geometry is uniquely **4064×2286**. Exact wrapper code consumes that as image width/height, and exhaustive decoding of the installed Surface sensor modules shows that only **OV13858 mode 1** has 4064×2286. None of the IMX681 modes does. This replay therefore remains byte-exact but is a **rear/shared-Tintless oracle, not front sequential-state evidence**.

## Exact live callback and state boundary

The captured OV13858 rear mode-1 stream reaches the embedded Surface Tintless callback at DeviceMFT RVA **`0xc95fd0`**. The deeper stateful core is RVA **`0xca01b0`**. The exact SHA-pinned `QcDeviceMFT8380.dll` is executed offline under ARM64 Unicorn; no reimplementation of the Tintless math is used for parity.

For both request5 and request6 the callback ABI is:

- `x0`: Tintless interface object;
- `x1`: bounded algorithm input/config object;
- `x2`: request-local stats/config source;
- `x3`: input 4×221-float mesh descriptor;
- `x4`: output 4×221-float mesh descriptor.

The four input meshes are read-only across the callback. The callback mutates its wrapper state, persistent context and the separate `0xdf0` output mesh.

## Stateful carry is exact

The Windows captures prove that request5 post-state is **byte-identical** to request6 pre-state for both:

- wrapper state: `0x1100` bytes, SHA256 `80149f9dc3df9c7f7b3856b5226c1994c77f3619ac00ad9335073690c066a6d4`;
- captured persistent context prefix: `0x4000` bytes, SHA256 `f30e829d54e1da8664f1c1722d34b71f151cd308d208b9400daf87188359b570`.

This closes the earlier ambiguity about “use previous” behavior: request6 must consume the state generated by request5, and the offline replay does exactly that in one emulator instance.

## Exact offline replay result

Request5 replay returns success and reproduces Windows byte-for-byte:

- wrapper state: exact;
- captured context prefix: exact;
- output mesh `0xdf0`: SHA256 **`1978d282a472117a2b28a3fb1c4b41295e1b8190c4737b448373e5571f381490`**.

Keeping that generated state alive and replacing only the request6 frame-local inputs, request6 also returns success and reproduces Windows byte-for-byte:

- wrapper state: exact;
- captured context prefix: exact;
- input/config buffers remain read-only and exact;
- output mesh `0xdf0`: SHA256 **`547d96e50a6775eff44c1af3085905c6c45705d1c59121a2b0eac7be58566824`**.

All compared buffers have **zero differing bytes**.

## Context footprint and scratch independence

Dynamic memory instrumentation of the exact callback shows the request5 and request6 paths access the persistent context through:

- highest read end, exclusive: **`context+0x12694`**;
- highest write end, exclusive: **`context+0x126e8`**.

Only the first `0x4000` bytes were captured from Windows. The extension above `0x4000` was therefore tested twice in a fresh replay: once initialized to `0x00`, once hostile-filled with `0xa5`. Both complete request5→request6 sequences produce the exact same Windows post-state and output meshes. The extension is consequently scratch/derived state for this path, not an additional Windows oracle input.

The emulator also models the normal Windows ARM64 large-stack helper at DeviceMFT RVA `0x1440` with a minimal synthetic TEB (`x18`, stack-limit at `TEB+0x10`). This is runtime infrastructure only; no DeviceMFT instructions are patched.

## Boundary after camera-identity correction

For the **rear OV13858 path represented by this capture**, sequential Tintless is closed byte-exactly and remains directly useful to rear parity.

For **front IMX681 parity**, this replay cannot satisfy the integrated producer gate. The front stream has independent 3840×2160 geometry and front-specific request state; it still needs a same-front-stream sequential Tintless capsule bridging the verified front calibrated/geometry input to the verified front staging output. Do not mix this TINTCTX state with LSCTRIGSRC or `E003H_ADAPTIVE_0073_LIVE_20260902`.
