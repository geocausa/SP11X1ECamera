# E004nz — SP11 OEM AVStream orchestration: static request, packet and start/stop handoff

**2026-09-24; parent `bf70ebaa7f01a509b511cd3869e5ea08eb9a7352`.** This experiment advances the pinned [Windows→native Linux stack map](../../../docs/CAMERA-STACK-PORT-MAP.md) at Windows slices W1–W4/W6–W8 and proposed Linux L1/L2/L3/L4. Everything here is **read-only, source-checked static evidence from the original same-SP11 OEM driver**, not evidence of a particular callback executing during an actual Windows session, and not a Linux native rear 4K frame. The owner-facing goal is a **native, controllable Linux stack without Windows services, Studio Effects, AI image enhancements, or transplanted Windows driver/firmware code**.

## What the first-party Windows binaries actually establish

The exact private `surfacecamavs8380.sys` is **547,192 bytes**, SHA256 `b97c4338c7c8868b9f3b73a34f6aea338ae6ab2a773bfd65f3b8fd31941577ed`. The UTF-16 OEM INF installs separate `QCCamAvs` AVStream kernel service, names **rear/front/aux** sensor identities and logical **preview/still/video** pins, and **registers** `QcDeviceMFT8380.dll`. The INF's long `OEMCameraProfiles` guidance is **commented explanatory syntax**, not an active profile assignment in that INF. Other installed components/registry settings and the driver itself may define profiles: the exact profile selected by our Windows `VideoRecord` session remains **unknown**. MFT registration does not establish it was loaded or sent a hardware command.

The binary's real imports include `KsInitializeDriver`, `KsCreateFilterFactory`, `KsFilterCreatePinFactory`, `KsPinAttemptProcessing`, `IoBuildDeviceIoControlRequest` and `IofCallDriver`. Those imports support an AVStream logical request/physical device-control boundary; **an import alone cannot identify the receiving driver or establish execution**. The original diagnostics and disassembly give substantially narrower anchor locations below.

### Engine start/stop selector sequence (source-verified, **not yet semantically decoded**)

The same helper RVA `0x20DA8` validates an input object and calls a function pointer (its two internal `blr x15` sites at `0x20DF4` and `0x20E30`). This proves an actual **indirect dispatch seam** inside the AVStream binary. It does **not** prove the recipient is `qccamisp8380.sys`, a sensor, or a directly issued IOCTL without tracing the backing interface object. OnStart submits in code order: `0x804, 0x804, 0x5, 0x17`; OnStop submits `0x805, 0x809, 0x805, 0x18`. Intermediate flags, optional branches and errors can skip individual calls, so these are **potential ordered call sites**, not guaranteed four calls every time.

These selectors are retained as **scalar evidence for the next static trace**, not instructions to implement or execute on Linux. To label one as a sensor/ISP operation, first trace the helper's interface object and receiving callback plus its argument shape. Only then compare the active Windows session and independently implement the necessary native hardware sequence. The exposed `IoBuildDeviceIoControlRequest` / `IofCallDriver` imports are useful leads but must not be assigned to a selector without a traced call edge.

## Evidence production and safety

`extract-static-callgraph.py` checks the **entire original driver SHA**, exact ARM64 machine type, **23 named diagnostic string RVAs and their independent `ADRP+ADD` xrefs**, **eight selector-to-common-dispatch call pairs**, and **four dispatch-helper instructions**: **66 source-checked ARM64 instruction anchors**. It also decodes only the original same-SP11 UTF-16 OEM INF, checking active service/sensor/pin/MFT declarations and rejecting active profile-registry assignments in *this* INF. Its sole export, `RESULT.json`, consists of **safe derived scalars, booleans and RVAs**. The proprietary binary, detailed diagnostics, Windows user-mode payloads, tuning, driver code, optical images and KD logs remain **private on their original machine**. Re-running with no `--write-new` verifies the saved scalar output rather than overwriting it.

No Windows session, webcam/CSI/IOMMU/MMIO DMA, KD, kernel build, module install or boot is invoked by this experiment; Golden FullIO v19c and front native PIX/rear RAW/software fallback are unchanged. The E004nr–E004nv rear native ISP sources remain compiled **uncalled** and runtime denied. Both active rear interrupt mode and BF event/WM16 actual completion still require separate runtime proof; Linux-native rear hardware-ISP 4K optical frames remain **unproven**.
