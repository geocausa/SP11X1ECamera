# E004gu — locate OEM PMIC timer-origin evidence and eliminate false Ghidra dispatch leads

Every original Windows OEM SYS image was inspected as a read-only file on protected SP11 Golden.

## What was genuinely narrowed

1. The original, SHA-pinned qcpmic8380.sys binary has one *explicit contiguous four-register address table* for the 32-bit entries 0xee3e, 0xee3f, 0xee40 and 0xee41 at PE RVA 0x36d48 (file offset 0x35948). A scan of all 102 locally archived Windows DriverStore SYS files finds this 16-byte address sequence **only** in qcpmic8380.sys. This locates that particular table; it does not exclude drivers computing addresses arithmetically, using other register tables or firmware/secure-world writers. These 102 files are the archived files available locally, not an exhaustive inventory of every component ever capable of programming the PMIC.
2. Ghidra 12.0.4 of the exact OEM PMIC PE recognized three references to the table at RVA 0x36d48: code RVAs 0x26e2c and 0x26e60 in the four-channel timer callback, and 0x27010 in the distinct single-channel timer callback. Original pinned ARM64 instructions confirm these load an address from the table and eventually call the PMIC masked-write helper RVA 0x23968. This is the observable **direct table-based software path**; it does not exclude a generic PMIC caller or indirect/data-created address outside the table.
3. Apparent *extra* Ghidra xrefs to the two timer callback entry points at RVAs 0x364c4/0x364c8 and 0x3faa0/0x3faa8 do **not** identify new runtime dispatchers. The first pair is in the original PE's 438-entry Guard CF **allowed-function metadata** table beginning at RVA 0x36218. The second pair is in PE .pdata **unwind function-start metadata**. The actual four-/single-channel timer callback pointers for this object are the 64-bit addresses at RVA 0x39498/0x394a0 in .data, independently pinned in E004gp. Without distinguishing these PE metadata tables, a naive search would overcount timer "callers".
4. Across executable .text/PAGE/INIT sections of the four named hash-pinned Windows qcpmic8380.sys, qcpmicapps8380.sys, qccamflash8380.sys and qcpmicglink8380.sys images, a literal ARM64 MOV immediate 0x93 is absent from the first three and occurs once, in an unrelated-looking glink context at RVA 0xc740. **This is not a whole-program search for computed value 0x93 or configuration data, and does not establish a reset default or eliminate Windows-side initialization**.

Together with prior **actual observations**, E004gt recorded no hits in two PMIC timer callbacks, the flash timer wrapper or the separate flash configuration entry during one bounded, normal eight-frame Windows OEM preview, while E004gs found no PMIC timer callbacks after passive postboot hooks. E004gb had no timer accesses through its selected PMIC masked helper during its earlier twelve-frame preview. The once-consumed E004fx Golden idle read returned 0x93 at all four timer registers. All these facts can coexist if timer configuration precedes our breakpoints or is inherited/initialized elsewhere; **they do not identify which component wrote the four bytes or prove a measured 200 ms electrical or optical cutoff**.

**Next discriminating engineering question:** trace the first actual SPMI write to 0xee3e..0xee41 through the generic PMIC write path *during fresh Windows driver/firmware initialization*, or independently determine cold PMIC reset contents using suitable original hardware documentation. Setting the same four postboot function-entry breakpoints for another ordinary preview would repeat a completed observation, not answer the outstanding question. Do not infer a firmware or UEFI writer solely from missing hits in Windows code; dynamic generic-address writes remain possible.
