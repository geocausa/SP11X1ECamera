# E004nv addendum — BF producer → selected dispatcher → WM16 state → completion

**Read-only same-SP11 static analysis (2026-09-24).** Exact private OEM `qccamisp8380.sys` SHA256 `64463b4d78894fdeee01ce87b51e3153662243e3fdf16f87596579b58617c21c`. All locations below are driver-relative RVAs; no Windows driver image, camera pixels, buffer pointers, raw KD logs or proprietary tuning are committed. This **corrects the earlier incompleteness**: the original E004nv analysis identified BF event `0x0F`/group8, but did not trace its producer, actual indirect caller, alternate interrupt mode or the callback's **direct WM16 MMIO registers**.

## Mode-dependent entry and actual caller

At `0x222A0`, an incoming *device-instance index* is saved as `w24`, with range `0..3`. At `0x22380–0x22384` the driver saves a per-device configuration value from a resource table into `device+0x349C`. At `0x22464–0x22478` it compares that device-instance index with the saved threshold, and records `mode = (index >= threshold)` in `device+0x6B678`. **This is a conditional per-device dispatch mode, NOT a generic assertion about CPU/ISP hardware version.** The threshold's active rear-session value has NOT been observed. It also selects a mapped register window at `device+0x150`: **`MMIO_base+0xC00` when mode=0**, **`MMIO_base+0x1200` when mode=1** (`0x2247C–0x2248C`).

The registration at `0x19FA8–0x1A100` uses that mode to install either `0x1EF90` (**mode=0**) or `0x1C9D0` (**mode=1**) in the device's function slot `+0x6BD8`. The existing independent OEM event-worker code at `0x2399C–0x239BC` **loads this exact `+0x6BD8` slot and calls it indirectly**, passing the device object and an event/status record. This is an actual statically traced caller, rather than an unverified guess that the BF comparator is called from a particular WDF IRQ routine. A separate external-facing registration at `0x1A138–0x1A154` supplies wrapper callback `0x1A280` to a device-interface method; that wrapper at `0x1A2C4–0x1A2EC` forwards an external event to a registered callback. The precise origin of the first hardware/firmware status bit upstream of that external interface remains unverified.

The same mode chooses the per-event hardware-status extraction callback in slot `+0x6B6C0`: **mode=0 → `0x1D620`**, mode=1 → `0x1BFF0` (`0x1A094–0x1A0AC`). This difference is material: **event `0x0F` is established specifically in the mode-0 dispatcher; two clean Windows 4K frame runs do not prove the live rear camera selected mode 0**. The previously armed E004nw breakpoint at `0x1FC68` could not distinguish an absent BF status bit, a different selected dispatcher, or a disrupted debugger/camera session.

## BF event is generated from input status *bit 7*

In the mode-0 handler `0x1EF90`, `0x1EFE8–0x1EFF0` takes the incoming status pointer from `event_record+0x08`, and loads the pair of 32-bit status words at `status_pointer+0x04` and `+0x08`. At `0x1F048` **`ubfx w15,w2,#7,#1`** extracts bit 7 of the *second* status word. If it is set, `0x1F188–0x1F198` appends **event ID `0x0F`** to the handler's local event list. Thus this branch has an upstream input-bit gate; the existence of a BF handler does not guarantee that a rear 4K VideoRecord request supplies BF events.

At `0x1FC60` the handler compares the selected event against `0x0F`. It prints the BF-stats IRQ diagnostic; `0x1FC8C–0x1FC98` requests **independent FIFO index 8** through the same per-group dequeue helper at `0x26460`, and exits if no entry is available. The helper reads `device + (0x66B + group_index)×8`, checks the ring's pending count, returns its entry and advances the ring cursor (`0x26500–0x265A8`). The callback group is **not equivalent to ten separate per-WM interrupts**.

## The key direct WM16 clue: actual OEM BF register read

The mode-0 BF branch passes `event_id=0x0F` to the mode-0 per-event callback via slot `+0x6B6C0` (`0x1FCA0–0x1FCC4`). Callback `0x1D620` uses a 25-entry jump table at `0x1D7F8`; the entry for event `0x0F` points **specifically** to `0x1D710`.

At `0x1D710–0x1D728`, that branch reads `[device.register_window+0x1270]` into event-scratch `+0x4C`, and **`[device.register_window+0x1200] & 1`** into event-scratch `+0x48`. The earlier mode-0 selector establishes `register_window = VFE_MMIO_base+0xC00`; therefore the actual hardware register offsets are **`0x1E70` and `0x1E00` from VFE's mapped base**. The independent Linux CAMSS bus definitions establish `client_base=0xE00`, `client_stride=0x100`, and `WM_ADDR_STATUS0=0x70`—exactly **WM16 CFG0 at `0x1E00` and WM16 ADDR_STATUS0 at `0x1E70`**. This is the *driver's own direct hardware association* of BF event `0x0F` with WM16; it is stronger than correlating two diagnostics by name. E004nq's two Windows rear live capture windows independently show WM16's CFG0 `0x00020001` (enabled), but those snapshots alone cannot prove event `0x0F` occurred.

The BF branch passes `scratch = device+0x178` at `0x1FCA8`. Thus the callback's scratch `+0x48` is **`device+0x1C0`**, the exact byte read at `0x1FCC8` to decide whether to build extended BF completion metadata. That flag is **WM16 CFG0 bit 0** from the driver's *own register read*, not an unexplained software guard.

## Where a non-empty BF completion goes

After the group-8 queue pop and BF-specific register callback, the handler conditionally uses outstanding-entry matcher `0x25078` with the dequeued entry's `+0x08` identity and `+0x16` tag (`0x1FCDC–0x1FCE4`). Matcher `0x250A8–0x25168` compares up to six outstanding pairs, increments a matched-entry completion count, and clears its tracking slot when that entry's expected count is reached. This **does not alone prove** a physical WM16 image/meta buffer was delivered to the application.

The handler then stamps the completion record with **BF resource port `0x300D`** at `0x1FCE8`, copies the dequeued entry's identity/tag and associated data, retains the queued item in device state, writes **completion code `0x1A`** into its notification record, and calls the existing notifier `0x26340` at `0x1FD28`. The notifier itself uses an indirect interface callback and has an error/status return; this is a software completion/notification path, not an independently observed frame DMA fence. The BF `0x300D` resource also has separate static configuration/enable handling at `0x1D830`, resource-to-offset translation at `0x1E2D8`, and resource selection in a write-master programming routine at `0x27FB0`.

## Practical implications and remaining evidence

For a permitted future live trace, verify **(a) which device-instance/mode selects `0x1EF90` versus `0x1C9D0`, (b) whether incoming status word2 bit7 ever becomes 1 during verified rear-4K frame delivery, (c) whether FIFO group8 has a queued item, and (d) whether WM16's enabled/address-status read and outstanding-entry matcher produce a valid retire/notification**. The earlier BF-branch breakpoint alone conflated all four gates; merely counting normal 4K video frames only establishes group0 video delivery. The E004nx/E004ny controls gave 365/366 and 1,152/1,154 valid Windows rear 4K frame handles with NO KD, but **no live BF occurrence**.

A source-only Linux rear six-group candidate E004nv exists, but **do not attach its group8 acknowledgement to a real ISR, assume frame retirement, or install it into Golden** until the active dispatch mode, BF FIFO/event and safe WM16/statistics DMA lifecycle are verified. OEM static code demonstrates a route for BF, **not** which runtime mode is selected or that the route was exercised. The original private OEM binary and private KD logs remain on their authorised hosts; this document contains only public-to-project scalar code offsets, register fields, and derived call relationships.
