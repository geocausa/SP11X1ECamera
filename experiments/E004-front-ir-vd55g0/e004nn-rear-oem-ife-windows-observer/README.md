### Critical task-invocation audit

The experiment's **first Windows Scheduled Task was inadvertently executed twice**: manually using `Start-ScheduledTask` at 21:22:06, and again at its future `-Once -At (Get-Date).AddMinutes(1)` trigger at 21:23:05. The second run created a separate successful private metadata original `E004NN-rear-preview-vs-record-20260923-212305.json`; it overwrote the two `E004NN-LIVE-*.txt` markers. It was **NOT** included in the ETW stream described here. The first private JSON was written 21:22:28.687 and the ETW trace ended 21:22:28.381, whereas the second private JSON was written 21:23:26.938, after the trace. The original ETW and WinRT source evidence remain unambiguously attributable to the **first capture only**. The Windows Scheduled Task was immediately unregistered after detecting this mistake; no camera task or ETW capture was left running. `RESULT.json` explicitly states `windows_user_task_invocations_observed=2`, `original_windows_user_task_consumed_once=false` and proves the two first/second original time boundaries. Do not call E004nn a single-invocation task and NEVER sum its two WinRT files as one continuous recording.

**Windows task-arming regression guard for ALL future oracle work:** Never manually start a Windows Scheduled Task that also has a future trigger without both (1) an atomic script-ENTRY file `[System.IO.FileMode]::CreateNew` consumed-lock, created before any camera access and retained permanently, and (2) explicit task unregistration after the intended invocation. File-exists checks only at the Register/Start command do NOT prevent a later automatic trigger. Treat any unexpected original identity as consumed until proven otherwise.
