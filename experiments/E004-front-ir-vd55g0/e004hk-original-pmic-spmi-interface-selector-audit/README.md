# E004hk — original OEM PMIC ↔ SPMI interface and raw-transaction selector (OFFLINE PASS)

**2026-09-20. Exact original Windows ARM64 instruction/data audit, no new live PMIC/Windows/KD operation.** This follows the E004gy genuine early raw-helper breakpoint and E004gz/E004ha generic callback mapping, and identifies the *next lower software transaction boundary* beneath original PMIC raw-write helper `qcpmic8380.sys+0x23dc8`. It does not capture a first write to the flash timer register, prove that an original indirect transport callback actually executed during THIS offline stage, or establish a hardware/optical independent shutdown.

The original SHA-pinned `qcpmic8380.sys` contains GUID `72c96e71-eb2d-48e3-99ac-9894a59f9c4c` at RVA **`0x37058`**. At original PMIC code RVAs `+0x3938..+0x3974`, it constructs an indirect WDF interface-query call, passing **that GUID as x2**, destination PMIC module-global struct RVA **`0x3d010` as x3**, required size **`0x70` as w4** and WDF function-table offset **`+0x588`**. The exact original `qcspmi8380.sys`, SHA256 `b6a5868ec2450e713b9a5ada7b4e1a4a77c77427fedf0806fe3eb6541099523c`, contains the **byte-identical GUID** at RVA **`0xa1d8`**. At its code `+0x3ef8..+0x3f38` it builds a descriptor using that GUID and passes it into a separate indirect WDF table method at offset **`+0x720`**. These original instruction/descriptor facts identify the compatible interface handshake: the precise WDF method names and success of the handshake at runtime have **not** been independently verified by this offline stage. Do not confuse this lower bus-facing GUID with the separately proven flash/PMIC IOCTL GUID `20952871-af3d-4a8a-9e47-cb346507b95b` from E004hc.

The original PMIC raw helper entry RVA **`0x23dc8`** copies call arguments `w0/w1/w2/x3/w4` into saved bus/SID/register address/source buffer/byte count. After its original validation and index adjustment, the low-level request packs the register and bus/SID selector with two original instructions:

```text
PMIC+23ed8: w8 = normalized_sid | (bus << 4)
PMIC+23edc: w2 = supplied_register | (w8 << 16)
PMIC+23ee0: save packed w2
PMIC+23f14..+23f3c: reload packed w2;
                      x0 = [PMIC+3d030]  (interface-owned context)
                      x3 = original input bytes pointer
                      w4 = original byte count
                      x15 = [PMIC+3d040] (indirect interface callback)
                      call x15
```

The low-level pointer and context live **inside the 0x70-byte module-global output-interface struct queried earlier**; they are not a static direct call from PMIC to an address inside `qcspmi8380.sys`. E004gy already confirmed that **this PMIC raw helper executed** on a previous fresh Windows idle boot for unrelated register addresses, but that earlier trace did NOT record the live callback pointer, complete SPMI bus/SID routing or a timer write. E004hk proves only the code's potential routing and the location of its indirect call, **not** that the lower interface actually wrote anything, including a `0x93` byte. Firmware, another driver/transport or true PMIC reset state remain possible first-writer explanations.

The verifier also pins the exact four **original PMIC raw-helper direct `bl` caller sites** (`+0x23a04` masked helper, `+0x2fc54`, `+0x303b4`, `+0x32c2c` generic callback) and the original lack of a direct call to the last wrapper: it is published through the separate callback table E004ha recovered. Given **synthetically normalized** `bus=0`, `sid=1`, and 16-bit register `0xee3e`, the original packing expression produces selector `0x0001ee3e`. This is a **calculator fixture for debugger argument decoding**, not proof that Windows bus/SID values are the same as Linux SPMI `0-01` or that the Surface IR emitter is physically on that channel. Actual caller arguments must be recorded before applying that filter; a transaction may also cover the target via a multi-byte span whose start is below `0xee3e`.
