## Full-IFE resource class chooses original IFE worker handler

Original driver resource enumerator RVA0x31AC–0x3238 probes literal OEM resource names **`IFE0`** (RVA0x2FFE8) and **`IFE1`** (RVA0x30010). Each matching mapped full-IFE resource goes through the same common success path at0x3234 that increments original software counter w22; the enumerator writes w22 at0x3380 into global **RVA0x670FC** (also mirrored as counters at global0x670F0/+0x08). Therefore the full-IFE count comes from successfully discovered/mapped resources, **not** directly from the app's VideoRecord mode or CSID BF IRQ.

Actual original per-IFE worker/source endpoint constructor0x22278 stores worker instance index w24 at **device context+0x120** (0x2237C), copies global full-IFE count from 0x670FC into **worker context+0x349C** (0x22380–0x22384), then at0x22464–0x22478 compares `w24 >= count` and writes flag to **worker context+0x6B678**. Its later mode-dependent registration0x19FA8–0x1A100 selects **zero-mode handler0x1EF90** with conditional CSID BF event0x0F, versus **nonzero handler0x1C9D0** for a different class.

**Precise conditional:** for original source worker instance index1, *if both original IFE0 and IFE1 are successfully discovered/mapped in this same initialization (count≥2)*, then `1 >= 2` is false and worker flag+0x6B678 is zero, selecting the BF-capable 0x1EF90 handler. If the resource count were only1, the same instance1 takes nonzero handler. Original two rear4K live windows E004nq/pi physically showed CSID1 active and VFE1 WM16 enabled, but they **did not capture the private original per-driver resource-enumeration counter, callback pointer, BF event0x0F or per-frame queue record**. Do not turn this conditional source fact into a claimed dynamically observed rear4K handler.

## Independently, config word+0x8C bit1 selects type-1 CSID status *format*

The per-client original setup at **RVA0x16748–0x16768** loads caller/config record **+0x8C**, tests **bit1 (`0x02`)**, stores its `!=0` result into source-format flag **input config+0xE28**. A different initialization path RVA0x17D94–0x17E58 reads that flag and installs both the per-type1-context **preparer+0x200** and **normalizer+0x208** accordingly. Flag0 selects CSID status prep0x1B5F0, where `CSID_BUF_DONE_STATUS+0x8C & 0x07FFFFFF` is written as source status+0x0C, plus normalizer0x1B7D0 which moves status+0x0C to BF consumer record+0x08. Flag1 installs prep0x20B50, where the CSID raw status word is reduced by **mask0x1F**, and normalizer0x20CE0, so BF bit7 does **not** survive that branch.

This **config+0x8C bit1 → input+0xE28** predicate is **independent in the source** of the **resource-instance count → worker+0x6B678** predicate. There is no established equality between flags, no original live rear4K input config+0x8C bit1 recording or per-session mode-preparer selection; a BF-capable zero-mode worker alone is not evidence that its incoming type1 record carried BF bit7. The same-SP11 Windows physical LIVE1/LIVE2 captures **do** prove CSID1 BUF_DONE+0x8C bit7 physically set and unmasked, but snapshots cannot prove that the preparer/worker consumed it to emit event0x0F or that group8 FIFO8 WM16 completion/owner/frame/DMA/IOMMU fence occurred.
