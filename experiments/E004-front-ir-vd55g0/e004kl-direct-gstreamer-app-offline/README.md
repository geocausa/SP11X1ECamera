# E004kl — independent direct GStreamer application

The metered E004kj V4L2-to-stdout/Python-appsrc application path proved full bytes, but E004kk demonstrated heavy copy/scheduling overhead even without cameras. This new bounded app opens a selected V4L2 device with native GStreamer v4l2src, converts to I420 and validates every full application buffer, hashes privately for uniqueness, measures monotonic arrival cadence, and requires normal EOS. No pixel files or hashes are exported. GStreamer offsets are reported as offsets, not assumed physical sensor sequences.

Default input is a moving synthetic ball. Real devices require root and the NEW E004km isolated candidate command-line marker; Golden cannot run the live path. All sources have 1..2400-frame bounds, 1..240-second deadlines and at most three appsink buffers. This is an app consumer, not a persistent camera service or Windows ISP implementation.

Five offline tests cover moving front/rear full application frames, rejection of duplicate frames, Golden live-device refusal, count/deadline bounds and known-plane numeric quality statistics. A camera-free 120-frame direct rear app run before quality sampling received 120 distinct I420 4K frames in 2.93s of arrival span (40.6189fps), with EOS and zero Gst-offset gaps; an earlier 10-second command invocation timed out and was fully terminated, so this is not a repeatability or live-rate claim. Quality sampling exports numeric luma/chroma/clipping statistics every 30th frame at a 64-byte plane stride, never scene pixels; these statistics are not calibrated Windows parity evidence.
