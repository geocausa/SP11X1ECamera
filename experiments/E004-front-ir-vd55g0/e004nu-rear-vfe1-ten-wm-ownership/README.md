# E004nu — compiled rear-only ten-client VFE1 BUS and conservative frame ownership

Parent E004nt Git `6bc77a8119195bb968ec36f4aaa92b7a14e79894`; inherited original Windows physical oracle E004nq, compiled isolated rear graph E004nr, CSID1 IPP E004ns, and bounded 4K coherent-DMA candidate E004nt. **E004nu is real source-compiled Linux kernel code, not an enabled capture:** it fills the independent rear VFE1 BUS *configuration* and per-write-master ownership model, with no loaded module, live camera activation, image capture, front-path changes or Golden reboot.

## Why the front BUS path cannot drive the rear

The accepted E003h/E003i front-only BUS recipe in the integrated CAMSS kernel contains **nine** enabled write masters: WM0/1 FULL Y/C, WM2/3 DS4/DS16 and WM11/12/13/14/18 statistics. The E004nq OEM Windows rear physical VFE1 MMIO snapshots contain **ten** enabled WMs in BOTH independent rear 4K recordings: **0,1,2,3,11,12,13,14,16,18**. The additional WM16 is BAF autofocus statistics and its live Windows config is `WM_CFG=0x00020001`, `FRAME_INCR=0x2D00`, `IMAGE_CFG0=0x00190004`, `IMAGE_CFG2=0x20`, `PACKER_CFG=0x0A`. Merely replaying the front BUS recipe would omit an active rear DMA output and its buffer/completion lifecycle. This is in addition to the rear FULL differences already proven: Y3840×2160/C3840×1080, physical WM stride5120, frame increments Y0xA9D000/C0x559000 and combined relative 4K buffer `0xFF6000`.

`camss-vfe-e004nu-rear-ten-wm.inc` contains a **separate compile-time register table for all ten rear WMs** generated directly from the exact, identical two-phase `E004nr/WM-RESULT.json`. Every whitelisted field for all ten clients is retained, including full/DS/stat frame increments, packed dimensions, stride, packer, bandwidth limit, IRQ-subsample/drop settings, metadata and mode configs, secondary controls and lossy thresholds. The source does NOT contain a single Windows image/metadata DMA address. The E004nu validator parses each C initializer and checks every value against BOTH E004nr Windows live captures (not merely against a hand-selected subset).

`vfe680_e004nu_rear_wm_prepare_disabled()` is a **new standalone candidate static-programming routine** for VFE1 only. It checks source-derived ten-client identity and FULL layout, then reads all ten existing WM enable bits **before its first write**. If any client is already enabled, the routine returns `-EBUSY`, protecting the shared active front VFE1 hardware. Only with all WMs disabled does it write the source-locked static registers with the WM enable bit masked off. It writes **neither a dynamic IMAGE_ADDR/META_ADDR register nor an enable command**; no active caller references it. The existing front BUS code, configuration and 27-frame hardware proof are unchanged.

## Ten-WM candidate frame lifecycle, not a fabricated event map

The new `vfe680_e004nu_rear_frame_begin()`, `vfe680_e004nu_rear_frame_ack_wm()` and `vfe680_e004nu_rear_frame_retire()` are source-compiled but **have no runtime callers**. They model the exact expected set of ten write masters with an independent 10-bit pending mask. Begin requires a source-verified, whole-span, 32-bit address-safe E004nt private Linux 4K buffer before marking it in-flight. An acknowledgement requires a **separately verified WM identity provided by a future hardware event decoder**; unknown or duplicate WM acknowledgements fail closed. A frame cannot release its buffer until every one of the ten pending clients, including WM16, is explicitly accounted for **and** the future caller has independently verified that the hardware BUS is stopped. The model never assumes that front VIDEO event 0x03 also retires rear BAF WM16, that ten per-WM IRQs exist, or that a guessed event order is valid.

**The rear WM16 event identity and its grouping with any other WM are still unknown.** The final Windows static WM register snapshots do not prove a completion interrupt map. In particular, the new model must NOT be installed into a real ISR or used to return a V4L2 buffer until an actual rear source-backed event-to-WM/group map, in-flight metadata/aux allocations, hardware stop/IRQ retirement and safe free-after-quiescence are established. On hardware error/timeout, leaving a buffer in-flight is safer than prematurely returning it for reuse; a future separately validated hardware-stop/recovery path is required.

`vfe680_e004nu_rear_wm_runtime_authorization()` **unconditionally returns `-EOPNOTSUPP`** after target/contract checks. No new rear stream, probe, V4L2, sysfs or module-param entry point is added. The source compiles into an isolated ARM64 CAMSS module and is never installed or loaded on the protected Golden kernel.
