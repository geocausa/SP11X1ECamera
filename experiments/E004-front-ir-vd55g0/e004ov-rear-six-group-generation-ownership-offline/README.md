## Concrete defect caught before runtime activation

The previous [E004nv source-compiled but unwired candidate](../e004nv-rear-six-group-bf-static/README.md) models six independent logical completion groups with a 10-WM pending mask, and correctly remains runtime-DENIED. However, its `vfe680_e004nv_rear_frame_ack_group(frame, verified_event_id)` interface **has no per-owner epoch, frame generation or group-specific queued-entry identity argument**. Connecting that source-only API directly to a future asynchronous IRQ stream could permit a late old-frame event to acknowledge the wrong new frame. Its `retire(..., independently_verified_bus_stopped)` similarly has a single externally provided Boolean, not a traceable source/IRQ/bus/IOMMU-generation evidence record. These are *prospective design risks*, not a claim that the existing unwired code mis-retired an actual frame.

E004ov adds a **separate standalone C11 model** `rear-stop-ownership.h` and tests; the original E004nv include, accepted Linux CAMSS kernel files, live ISR, V4L2 and module are **unchanged**. The model is NOT integrated with or included by CAMSS, and provides no runtime camera authorization.

The per-group queue ID is a **Linux design input**, not a claim that Windows supplies a common frame tag or that any BF queue event occurred during existing Windows captures.
