## Actual native integration, not just a simulated gate

The accepted native camss-csid-680.c ISR already latches CSID BUF_DONE+0x8C into buf_done_val, writes the SAME value to the existing clear register+0x94, then handles existing front statistics and full-CSID RDI completions. The existing CSID1 BF bit7 currently gets cleared but has no dedicated BF consumer. The real accepted VFE680 ISR remains a no-op, and a CSID BF bit is neither proven to identify an exact queued WM16 buffer nor to guarantee DMA/IOMMU completion.

The E004pt **isolated COPY** of CAMSS adds one call e004pt_observe_csid1_bf_irq(csid,buf_done_val) immediately after the EXISTING clear. It is restricted to non-lite CSID ID1, the already-latched bit7 and a local, per-CSID atomic observation counter and last status word. A read-only diagnostic symbol csid680_e004pt_bf_status_observations is compiled and has no runtime caller. The counter is explicitly NOT a per-frame, rear-only, WM16 or safe-completion count: CSID1 may serve the front camera, no owner, FIFO8 generation, WM16 buffer or DMA identity is attached, and even its monotonic software counter cannot establish IRQ event-to-buffer ordering. The observer adds **no MMIO read, additional IRQ acknowledgement, CSID reset, camera configuration, per-frame completion, vb2_buffer_done, DMA unmap or buffer reuse**. The existing generic RDI14–17 path and front code are preserved.

The isolated candidate header adds only counter storage, a diagnostic prototype and initialization; these changes are NOT present in the accepted CAMSS tree, deployed module or protected Golden. The E004nv six-group rear candidate is still compiled but unwired and runtime-DENIED. Even an observed BF bit7 from a future non-Golden test is only status-domain evidence, not an independently proven WM16 bus-completion fence. No real source provider for FIFO8 outstanding queue identity and same-frame/owner DMA-safe completion was added.
