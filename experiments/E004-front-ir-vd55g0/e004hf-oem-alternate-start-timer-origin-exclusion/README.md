# E004hf — alternate OEM flash start callers and the fixed helper's timer-request values (OFFLINE PASS)

**2026-09-20. Original Windows ARM64 static findings, reconciled with E004he and earlier E004fi/fl/gi/Ghidra work. No additional Windows, KDNET, camera or PMIC test.** This is a direct-call/control-flow and **specific fixed-helper-output** exclusion, not a full original timer-register first-writer attribution.

The original hash-pinned `qccamflash8380.sys` has exactly TWO direct ARM64 `bl` calls to its alternate flash-start routine RVA **`0x48c8`**: caller **`0x6638`** in its general configuration function (entry `0x63f8`) and caller **`0x6a20`** in another state-dependent event function (entry `0x6890`). The general configuration validates a 12-byte input, stores context values in globals at offsets `0x68`, `0x6c..0x70` and `0x74`, then reaches `+0x6638` after checking the saved context words. The event path reaches `+0x6a20` only after its original byte-`0x88` zero branch and byte-`0x81` equals-one check; a different branch calls the OFF routine `+0x4828`. These are original ARM64 **branch predicates**, not yet a proven mapping from Windows Camera public UI, face unlock, or Windows kernel PnP operation to an observed invocation. They make it incorrect to claim the subtype-0 *direct* branch is the entire possible flash lifecycle.

The alternate-start `+0x48c8` explicitly calls current `+0x4ce0` → timer helper **`+0x4dd0`** → strobe `+0x4d58`, with software return checks. The **only two direct calls** to original flash timer helper `+0x4dd0` in the scanned flash executable remain `+0x4938` (this alternate start) and `+0x5b2c` (the type-2 branch); E004he already showed that the selected subtype-0 *direct dispatch* at `+0x5b7c..+0x5c64` does not itself call that helper. This does NOT rule out an earlier/indirect invocation of the alternate-start function in an OEM lifecycle.

The original timer helper's enabled request uses **two fixed 32-bit interval words `0x4f6` (1270 nominal ms)** encoded in the 16-byte input to IOCTL `0x802f0fac`; it writes enabled selection bytes `[1,1]`, or disabled `[0,0]`. The original PMIC timer callback `+0x26d50` (now tied to the independently live-confirmed OEM four-channel dispatch table through E004hd/E004he) uses software encoding `0x80 | floor((ms-10)/10)` on enabled 10–1280 ms requests and zero on disabled ones. Thus the **specific flash helper's direct enabled 1270-ms request would encode `0xfe`**, or a disabled request `0x00`; **neither is `0x93`**. This excludes this specific fixed helper *as an origin of a newly requested `0x93` value under the verified software path*, not the possibility that a previous `0x93` remains in hardware when the helper is not called or that a different Windows/firmware/PMIC callback constructs a 200-ms timer. It does not prove whether any of these requests executed on the actual SP11 normal IR preview or how the actual hardware times/terminates light emission.

The original `0x93` was separately captured **once** in E004fx as four *idle configuration bytes* of the disabled Golden flash-controller's PMIC registers, not a timer-register first-write trace or an optical pulse. E004gb's single bounded Windows subtype-0 OEM camera preview recorded no timer-address requests **at the selected helper hooks**; these previously consumed observations were NOT repeated in E004hf.
