# E004hi — bounded native ARM64 offline per-frame HLOS C stream with terminal session commitment

**OFFLINE FUNCTIONAL PASS (2026-09-20). No camera, PMIC, IR emitter, Windows, kernel, login, face enrollment or installation.** This stage addresses the actual E004hh performance/latency trade-off with a NEW, explicitly **diagnostic-only** stream transport. It reuses the EXACT maintained original HLOS C pixel core from E004gr/E004hg/E004hh and adds separately named `src/sp11-camera-hlos-worker/sp11-offline-nv12-stream.c` plus an unprivileged `sp11-offline-stream-client.py`. The new native C sidecar is compiled and executed **only in an automatically removed /tmp directory**; the original single/batch C executable and underlying pixel algorithm remain unchanged.

## Strict in-memory protocol and failure semantics

The C sidecar requires `--frames N`, exactly 1..16. For each frame, the offline Python client sends an eight-byte `IN01` + little-endian 1-based index followed by EXACTLY one 644×604 immutable grayscale NV12 frame (all chroma bytes `0x80`). The C sidecar checks the header, monotonically increasing expected index, input length/chroma, runs the actual original `sp11_parity_worker_run` processing algorithm and writes an `OUT1` + same index header and one exact complete processed frame. No next frame is sent until the client has read the prior complete response, and source/destination/scratch buffers are wiped between frames.

**Outputs are PROVISIONAL, not a completed session.** After exactly N provisional outputs, the client must close the input pipe. C checks EOF without trailing bytes and *then* emits `DONE` + expected N and exits zero. The Python client accepts the session as complete **only after exactly matching DONE, clean stdout EOF and original child exit status zero**. A malformed *first* frame produces no frame output; if a **later** frame/header is malformed or extra bytes appear after the last provisional output, C returns nonzero **without DONE**, so the whole session—including previously delivered provisional frames—must be discarded. This is a protocol contract for an offline diagnostic client, not an external authenticator: no consumer may use provisional output as a biometric acceptance decision. A malicious consumer that ignores this rule would defeat it; a future production authenticator requires a separate trusted transport and independently validated provenance.

The Python client validates exact immutable frame bytes/neutral chroma, strict sequential index and one-shot state. A caller-monotonic 30-second (configurable 0.1..120s) deadline bounds operations **only while the caller runs**. On wrong input, out-of-order packets, incomplete pipe output, timeout, abort or unexpected process status, it kills/reaps the disposable subprocess and becomes a terminal, non-rearmable **fault**. This is NOT an independent watchdog if the host itself stalls, crashes, or stops calling methods; it has no GPIO/LED/PMIC/camera interface.

## Actual SP11 ARM64 verification

The exact original SHA-pinned public OpenCV Zoo visible-light demo image was converted in RAM to the same 644×604 grayscale/neutral NV12 ROI used in E004gr/E004hg. The new stream sidecar and original unmodified one-shot C executable were both compiled with `clang -O2 -Wall -Wextra -Werror` from the unchanged original eight-file C core in a disposable directory. **All eight streamed frame outputs were byte-for-byte identical to the original maintained single-frame C output**; every processed frame passed the original strict full-range NV12 bridge to the **real original YuNet/SFace** OpenCV 4.12 ARM64 models and yielded one ephemeral finite 128-dimensional public-demo feature. No raw image, NV12/BGR frame, feature/template, match score or identity was saved in Git or the diagnostics output.

Actual original-C rejection tests: wrong first index, wrong first header, short first input and nonneutral chroma all yield no output; invalid `--frames 0/17` also yield no output. For bad second index, truncated second frame or trailing data after a valid first frame, C can emit that *first provisional frame* but returns nonzero with **NO DONE**. The diagnostic client likewise rejects invalid constructor counts, wrong order/type/chroma, a caller-driven deadline expiry and a malformed later frame, without allowing a faulted or completed session to rearm. The main experiment ran **9 original-C negative scenarios and 8 terminal-client negative scenarios**; `test_stream.py` independently rejects **12 malformed constructor/deadline inputs**. The archived `verify_result.py` checks original C/model/source hashes and the explicit absence of authentication, freshness, liveness and physical safety claims without requiring model assets.

One single observed eight-frame stream trial, after model warmup, reported **139.614 ms** to its first provisional public model feature, **1,091.276 ms** to its eighth provisional feature and **1,093.439 ms** to DONE/clean process-exit confirmation. This does **not** establish any performance improvement over E004hh's four-pair earlier benchmark (which was taken under different scheduling/cache conditions); in fact this initial session did NOT produce a faster interactive or eight-frame result than the earlier reported median. Separate **same-session alternating paired** single/batch/stream measurements are required before choosing an optimized transport. None of these repeated-public-fixture timings represents a genuine sensor stream, 60-fps capture, near-IR face recognition, spoof detection, enrollment or identity acceptance.
