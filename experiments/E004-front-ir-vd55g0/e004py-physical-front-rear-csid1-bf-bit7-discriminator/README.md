**What this narrows:** Unlike an unscoped CSID1 bit7 counter, an owner/mode-tagged future native BF observer can use the independently established camera owner/sensor/source mode *and* verify a latched bit7 within that scope. In the four Windows source samples, BF bit7 co-occurs with active rear WM16 and does not appear in sampled front, while the other sampled BUF_DONE bits and mask stay identical. But mode correlation is not per-event causation or proof that front could never generate BF bit7 at another instant. Never attribute an arbitrary CSID1 IRQ to rear solely because bit7 is set; shared front/rear hardware requires a separately attested exclusive owner epoch.

**What remains unproven:** Live original rear4K *selected* config-zero event preparer and BF event0x0F delivery; nonempty, actually initialized FIFO8 group8 entry; NONNULL outstanding WM16 pointer/tag matched to that same original device/owner/frame; independently verified correct-buffer CSID- or VFE-delivered WM16 hardware bus IRQ/ACK, DMA/IOMMU completion and six-group stop.
